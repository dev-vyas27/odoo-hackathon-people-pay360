# Data model — PostgreSQL

Owner of this file: **Dev A**. The authoritative schema is the SQL in
[`migrations/`](../migrations/); this document explains the decisions behind it.

## How migrations work

```bash
npm run migrate              # apply everything pending
npm run migrate -- --status  # what is applied, what is not
```

Two rules, both enforced by [`scripts/migrate.ts`](../scripts/migrate.ts):

1. **Never edit a migration that has been applied.** The runner stores a
   checksum and refuses to continue if a file it already ran has changed —
   at that point the database and the repository disagree and only one of them
   knows which is right. Add a new numbered file instead.
2. **One file per domain, one owner per file.** Three people adding
   `0010_*.sql`, `0011_*.sql` and `0012_*.sql` never touch the same bytes.

Each file runs inside its own transaction, so a migration that fails halfway
leaves nothing behind. An advisory lock stops two processes applying the same
migration at once.

cyclic (`departments.manager_id` ↔ `employees.department_id`,
`contracts.salary_structure_id`). Those are resolved by creating the column
first and adding the constraint in a later file — see the end of `0004_people.sql`.

## Conventions

| Rule | Why |
|---|---|
| `snake_case` in SQL, `camelCase` in TypeScript | Translated in exactly one place per table: the repository's `toDomain` mapper. That is what stops `employee_id` reaching a React component. |
| Primary keys are `uuid DEFAULT gen_random_uuid()` | Generated by the database, not the application, and stable across environments. The seed relies on being able to *choose* ids — see below. |
| Money is `numeric(14, 2)`, **never** `float` | `0.1 + 0.2 <> 0.3`. A one-paise drift across 500 payslips is unfindable at 3am. `lib/db.ts` parses `numeric` to a JS number on the way out. |
| Calendar days are `date`, moments are `timestamptz` | "The 3rd of March" is not a moment in time. Storing it as one reintroduces every timezone bug `Period` exists to prevent. |
| Status columns are `text` + a named `CHECK` | Both `CHECK` and native `ENUM` are correct. `CHECK` was chosen because adding a value is an ordinary `ALTER TABLE`, whereas `ALTER TYPE ... ADD VALUE` has transaction-block restrictions that are awkward inside a migration runner. Permitted values mirror the `as const` arrays in `modules/shared/contracts/`. |
| Every table has `created_at` / `updated_at` | Maintained by the shared `set_updated_at()` trigger, so an application bug cannot skip it. `created_at` is the default sort for every list endpoint. |
| Foreign keys always declare `ON DELETE` | `RESTRICT` where history must survive (payslips, contracts), `SET NULL` for optional links, `CASCADE` only for rows that are meaningless without their parent (schedule days, payslip lines). |
| Values are **always** `$1, $2, ...` | The entire defence against SQL injection. Identifiers cannot be bound, so any generated column name is checked against an allowlist first — see `BaseSqlRepository`. |

## Decisions worth defending

These are the answers to "why is it like that", which is the only question a
schema review actually asks.

### `timeoff_allocations.taken` is stored, not derived

Deriving it would mean summing every approved request on every balance read.
The real reason is concurrency: two approvals racing on one allocation would
both read the same "before" total and both succeed. A stored counter mutated
inside the same transaction as the status change cannot do that.

The domain enforces `taken <= allocated` in `Allocation.consume()`. The table
restates it as a `CHECK`, where nothing can bypass it.

### `contracts` uses an EXCLUSION constraint

The spec requires "avoiding concurrent active contracts". An application-level
"does one already exist?" check can never guarantee that — two requests can both
read "no" before either writes.

```sql
EXCLUDE USING gist (
  employee_id WITH =,
  daterange(starts_on, ends_on, '[]') WITH &&
) WHERE (status = 'active')
```

No two `active` rows may share an employee and overlap in time. `'[]'` is
inclusive at both ends, matching the `Period` value object; a `NULL` end
produces an unbounded range, so an open-ended contract correctly conflicts with
everything after its start.

### `attendances` has `UNIQUE (employee_id, worked_on)`

Duplicate attendance silently doubles worked days, which silently overpays a
payslip. One row per person per day is an invariant, so the database holds it.

### `payslip_lines` is a table, not JSON

Line items are aggregated ("total HRA paid this quarter"), have a fixed shape,
and are the single most-inspected part of the system. A JSONB blob would make
them opaque to SQL.

They are also a **snapshot**: the computed amount is stored, not a pointer to
the rule that produced it. Editing a salary rule next quarter must not silently
rewrite last quarter's payslips. That is the difference between a payroll system
and a spreadsheet.

### `users` is separate from `employees`

A user is a credential with a role; an employee is an HR record. Not every
employee has a login, an admin may have no employee record, and "disable the
login but keep the payroll history" has to stay possible.

`users.email` is unique via a **functional index** on `lower(email)`. A plain
`UNIQUE (email)` would accept `Admin@x.com` alongside `admin@x.com` and produce
two accounts that look identical on screen.

### `working_schedule_days` is a table, not a JSON column

It is queried ("which schedules work Saturdays"), validated per row, and has a
fixed shape. `UNIQUE (working_schedule_id, day_of_week)` stops a duplicate row
silently doubling the computed weekly hours.

## Seeding

[`scripts/seed/ids.ts`](../scripts/seed/ids.ts) produces **deterministic UUIDs**:

```
seedId('emp', 7)  ->  656d7000-0000-4000-8000-000000000007
                      ^^^^^^ ASCII "emp"
```

Dev C's payslip can reference Dev B's employee #7 without Dev B's seed having
run, and re-seeding updates the same rows via `ON CONFLICT (id) DO UPDATE`
rather than duplicating them. The version (`4`) and variant (`8`) nibbles are
set so Postgres accepts them as well-formed UUIDs.

The whole seed runs in **one transaction** — either the demo database is fully
populated or it is untouched. There is no half-seeded state where users exist
but the leave they reference does not.

Add your data as `scripts/seed/parts/<module>.seed.ts` and register it with one
line in `PARTS`. See [`scripts/seed/README.md`](../scripts/seed/README.md).

> `parts/people.seed.ts` is a **placeholder owned by Dev A** with five
> employees. It exists only because foreign keys are real: identity and timeoff
> cannot seed until something has put employees in the table. Dev B should
> replace it wholesale, keeping the ids from `SEED`.
